# limnoria-mcp

A **local, authenticated FastMCP plugin for Limnoria**, with an independent
service-control MCP and a companion mcp-js NixOS module.

This is an administrator/developer interface, not a public IRC command gateway.
No arbitrary shell strings, arbitrary systemd units, or arbitrary IRC commands
are accepted.

## Architecture

```text
MCP client → companion mcp-js → limnoria-mcp-control (stdio)
                               ├─ confined managed-plugin filesystem (works offline)
                               ├─ on-demand authenticated loopback HTTP
                               │    → MCPBridge inside Limnoria → load/reload
                               └─ fixed service-control helper → Unix socket broker
                                    → one configured systemd service
```

The controller declares its tools without connecting to the bot. Start, stop,
restart, status, recent logs, and plugin file repair therefore remain available
when Limnoria is down.
The bot plugin uses standalone FastMCP's native Streamable HTTP
transport at `http://127.0.0.1:8765/mcp`. It rejects browser Origin headers and
requires a bearer token on every request. Do not expose this port publicly.

### Tools

| Tool | Scope |
|---|---|
| `list_plugins` | Managed plugin directory names |
| `read_plugin_file` | One bounded UTF-8 managed source file |
| `write_plugin_file` | Atomic source write, Python syntax checked |
| `load_plugin` / `reload_plugin` | One managed plugin, scheduled on the bot loop |
| `service_action` | Exactly `start`, `stop`, or `restart` |
| `service_status` / `service_logs` | One configured service; bounded recent logs |

Managed plugin names match `Agent[A-Z][A-Za-z0-9_]{0,48}` (e.g. `AgentHello`).
Files are limited to `__init__.py`, `plugin.py`, `config.py`, and `README.md`,
256 KiB each. Filesystem operations use pinned directory descriptors, reject
traversal/symlink reads/hardlink reads, and replace files rather than truncating
existing targets. Bytecode caches are invalidated on edits. `MCPBridge` and core
plugins are not writable through these tools.

## Trust boundary — read before enabling

**Writing and loading Python is arbitrary code execution as the bot service
account.** Path validation and the service-command allowlist constrain the tools;
they do not sandbox Python plugins. A loaded plugin can access anything the bot
user can access, including its IRC credentials and network connections. Only
trusted administrators/agents should receive this capability. Use a dedicated
bot identity, minimal credentials and OS service isolation. The companion must
not enable mcp-js native filesystem or subprocess modules as a substitute for
these tools. Its native path policy is not a symlink sandbox.

The control-plane code and privileged broker must be administrator-owned and
outside the writable plugin directory. Bearer tokens are supplied externally,
never generated by this project or committed. Logs can include private IRC
content; authorize clients accordingly. Service logs are bounded, not guaranteed
secret-redacted. Stopping/restarting interrupts IRC connectivity.

## Python installation and bot configuration

Python 3.11+ on Linux is required. Install the package into the bot's Python
environment; it registers the `MCPBridge` Limnoria plugin entry point.

```sh
python -m pip install .
```

Supply these environment variables to the Limnoria service:

* `LIMNORIA_MCP_PLUGIN_ROOT`: absolute path to an existing dedicated managed directory.
* `LIMNORIA_MCP_TOKEN_FILE`: externally provisioned readable token file (at least 32 characters).
* `LIMNORIA_MCP_PORT`: optional loopback port, default `8765`.

Add the managed directory to `supybot.directories.plugins` so plugins marked for
auto-load can load after a bot restart. Load `MCPBridge` through the normal
Limnoria owner interface. Keep the bridge installed read-only outside that path.

Run `limnoria-mcp-control` as an MCP stdio server with the same plugin-root/token/port settings
and `LIMNORIA_MCP_CONTROL_HELPER` pointing to the deployment's immutable helper.
The bot and controller need a dedicated shared plugin group; managed directories
use mode 2770 and files 0660. Use a group-writable umask (0007) and set
`PYTHONDONTWRITEBYTECODE=1` for both services. There is deliberately no generic shell fallback. See the NixOS module and
integration documentation for the complete companion deployment configuration.
Installation, credential provisioning and live deployment require administrator
authorization; merely building this repository does none of those things.

### Minimal managed plugin

Write `AgentHello/__init__.py`:

```python
from .plugin import Class
```

Write `AgentHello/plugin.py`:

```python
from supybot import callbacks
from supybot.commands import wrap

class AgentHello(callbacks.Plugin):
    def hello(self, irc, msg, args):
        """takes no arguments — replies with a greeting."""
        irc.reply("Hello from a managed plugin!")
    hello = wrap(hello)

Class = AgentHello
```

Call `load_plugin("AgentHello")`; after editing, call `reload_plugin("AgentHello")`.
Use a class matching the plugin directory name. Imports execute trusted Python;
failed imports restore old module registrations/callbacks where possible, but
arbitrary plugin side effects cannot be rolled back. A lifecycle timeout may
mean an operation is still running: inspect before retrying.

## Development

```sh
python -m venv .venv
.venv/bin/pip install -e '.[test]'
.venv/bin/pytest -q
```

Tests exercise authentication, MCP initialize/list/call, filesystem confinement,
fixed control argv, and actual Limnoria loading/reloading with synthetic fixtures.
They do not connect to IRC or manage live services. Nix evaluation/runtime checks
are separate; see integration documentation for validation status and limits.
